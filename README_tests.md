# Тесты для smart_export_2_0

Это дополнение к пользовательскому архиву, а не новая реализация сервиса.
Распакуйте содержимое рядом с папками python-ocr и go-file-sender.
Исходный код приложения не менялся. DATA и медицинские документы в пакет не включены.

## Фактический результат

Исходные проверки: Python 19/19, Go 12/12.
Добавленные проверки: Python 1 passed / 5 failed, Go 1 passed / 3 failed.
Общий запуск: Python 20 passed / 5 failed; Go 13 passed / 3 failed.
Итого 41 самостоятельный сценарий: 33 passed, 8 failed.
Go-родитель TestR5RejectInvalidQueueAcknowledgement не считается ещё одним сценарием поверх трёх subtests.

Падение ожидается как наблюдение текущего поведения. Тесты НЕ помечены xfail,
не содержат assert False и не изменяют приложение ради искусственного сбоя.
Возврат кода 1 при запуске означает обнаруженные расхождения.

## Какие требования проверены

R1 (расширение контракта): испорченное содержимое PDF/PNG отклоняется с 400 до Kafka.
Два случая не проходят: API возвращает 202 и публикует некорректные байты.
README проекта признаёт отсутствие проверки содержимого.

R2 (полнота OCR): PDF с заголовком и изображением на ОДНОМ листе сохраняет оба фрагмента.
Не проходит: extract_text возвращает только HEADER 12345 и review_required=false,
текст SCAN 98765 пропускается. Используется настоящий PDF, а не подмена extract_text.

R3 (расширение контракта сохранности): тот же ID с другими байтами не перезаписывает оригинал.
Не проходит: os.replace заменяет ранее сохранённый файл.
Это проверка конфликта ключа consumer, не заявление о вероятности UUID-коллизии.

R4 (расширение контракта повторов): один Idempotency-Key с тем же документом даёт один ID.
Не проходит: два запроса создают разные UUID и две публикации.
README проекта признаёт возможность дубликатов между HTTP-запросами.

R5 (расширение контракта подтверждения): Go принимает успех только при осмысленном JSON ACK.
Три случая не проходят: не-JSON, status=error, status=queued без document_id.
Сейчас sendFile проверяет только 2xx. Успешный HTTP 200 в исходных тестах не запрещается.

Добавлены положительные контроли: корректный PNG ставится в очередь,
корректный JSON queued с document_id принимается отправителем.

## Запуск Python

Из папки python-ocr:

    python -m pip install -r requirements-dev.txt
    python -m pytest tests/test_regression_contract.py -q
    python -m pytest -q

Первый запуск собирает 6 новых случаев, полный — 25.
Для исходных OCR-тестов необходимы Tesseract, rus+eng и DejaVuSans.ttf.
Новый mixed-page тест не требует реального запуска Tesseract на текущей реализации,
поскольку дефект состоит в пропуске OCR для этой страницы.
Kafka в тестах API заменён подтверждающей заглушкой. Живой брокер не требуется.

## Запуск Go

Из папки go-file-sender, Go 1.27.1:

    go test ./... -v
    go test -run 'TestR5|TestControl' -v

Родитель TestR5 имеет три дочерних случая. Полный запуск включает 16 самостоятельных сценариев.
Проверки используют настоящий net/http и локальный httptest.Server.

## Окружение проведённого запуска

Linux x86_64, Python 3.12.14, Go 1.27.1, Tesseract 5.3.4.
Зависимости приложения установлены по requirements.txt:
FastAPI 0.143.0, uvicorn 0.54.0, python-multipart 0.0.32,
confluent-kafka 2.6.1, PyMuPDF 1.28.2, Pillow 12.3.0.
Тестирование: pytest 9.1.1, pytest-html 4.2.0, httpx 0.28.1.
Точные версии смотрите environment.txt. Сначала были подготовлены языки Tesseract;
неподготовленное окружение не включено в итоговые результаты.

## Границы результата

Исправления приложения не вносились. Успешного повторного регресса после исправлений нет.
R1 и R3–R5 — предложенные усиленные критерии, часть из них уже обозначена ограничениями
прототипа. Их необходимо согласовать перед признанием нарушениями утверждённого ТЗ.
Проверка R2 показывает реальную потерю части содержимого в текущем OCR.
Docker Compose, живой Kafka, нагрузка, медицинская точность и интеграция МИС не проверялись.
